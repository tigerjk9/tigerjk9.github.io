AI 도구로 영상을 만들면 빠르다. 그러나 빨리 만든 만큼 빨리 어긋난다. 장면이 바뀌자 주인공의 옷이 달라지고, 대사와 컷 길이가 맞지 않고, 음량이 들쭉날쭉하다. 깃허브에 공개된 motion-video-production은 이런 문제를 단계마다 잡아내도록 짠 에이전트 스킬이다. 30~90초 모션 그래픽과 영상을 처음부터 끝까지 만드는 순서를 6단계로 나누고, 단계가 끝날 때마다 검사 스크립트가 통과 여부를 판정한다.

## 도구를 늘어놓는 것만으로는 영상이 되지 않는다

AI로 콘텐츠를 만든다고 하면 흔히 개별 도구의 성능에 눈이 간다. 이미지를 만들고, 대본을 쓰고, 목소리를 입히는 도구는 저마다 뛰어나다. 그러나 도구를 나열한다고 좋은 영상이 나오지는 않는다. 어떤 순서로 무엇을 만들고, 언제 멈춰 확인할지 정한 절차가 있어야 한다.

motion-video-production은 그 절차를 Agent Skills 형식으로 묶었다. Codex, Claude Code 등 스킬을 지원하는 코딩 에이전트에서 같은 폴더를 그대로 쓴다. 영상 제작을 요청하면 에이전트는 먼저 공개 방식, 길이와 화면비, 쓸 수 있는 도구, 금지 요소 네 가지를 묻고, `STORY.md`부터 단계 순서대로 진행한다. 생성 도구가 연결되어 있지 않으면 프롬프트를 건네주고 사용자가 만든 파일을 받아 이어 간다. 에이전트가 이미지를 볼 수 없는 환경이라면 사용자에게 직접 눈으로 확인해 달라고 요청한다. 모든 것을 AI가 알아서 하는 구조가 아니라, 사람이 개입할 지점을 처음부터 정해 둔 구조다.

## 단계마다 걸린 관문, gate.py

핵심은 `gate.py`라는 검사 스크립트다. 단계 산출물을 측정해 통과하면 종료 코드 0, 막히면 1(BLOCK)을 돌려준다. 막혔을 때는 `qa/gate-<단계>.txt`의 BLOCK 줄을 읽고 산출물을 고친 뒤 같은 게이트를 다시 실행한다. 파일이 있는지만 보지 않고 영상 길이, 프레임 수, 라우드니스 같은 수치를 직접 잰다.

| 제작 단계 | 게이트 | 하는 검사 |
|---|---|---|
| 1. 스토리·장면 기획 | `story` | 빈칸, BPM, 음악 싱크 지점 표(시간이 숫자인지), 장면 표 |
| 2. 캐릭터 시트 | `character` | `character.txt`가 한 문단 평문인지, 색 표현, 시트 이미지 |
| 3. 키프레임 | `keyframes` | 중복 파일, 클립과의 화면비 |
| 4. 영상 변환 | `clips` | 길이, 프레임 수, 시작 화면 일치, 프레임 스트립 생성, 클립별 판정 기록 |
| 5. 음악·목소리 | `audio` | 음성 ID 1개, 대사 파일 |
| 6. 조립 | `edit`, `final` | 박 격자, 컷 연결, 반복 컷, 대사 길이, 프레임 수, 오디오, 라우드니스, true peak, 검수 기록 |

교육용 영상이라면 이런 검사가 특히 쓸모 있다. 학습 영상의 캐릭터가 중간에 다른 사람처럼 바뀌는 문제는 클립 단계의 검수에서, 컷이 박자를 놓쳐 집중을 흐리는 문제는 조립 단계의 게이트에서 걸러진다. 완성본을 내보내기 전에 잡힌다는 점이 중요하다.

## 숫자로 못 잡는 것은 사람이 본다

<img src="/assets/motion-video-production-skill-harness-strip.jpg" alt="키프레임과 0초, 1초, 1.5초, 2초, 3초 프레임을 한 줄로 놓은 프레임 스트립. 1초부터 인물의 상의 색이 바뀐다">
<figcaption>프레임 스트립 예시. 시작 화면은 키프레임과 같지만 1.0초부터 주황 상의가 검은 상의로 바뀐다. (출처: unclejobs-ai/motion-video-skill)</figcaption>
</figure>

영상 생성 도구가 만든 클립은 시작 화면이 키프레임과 같아도 1~2초 뒤에 인물의 옷, 안경, 머리가 바뀌곤 한다. SSIM 같은 화면 유사도 값은 인물이 움직인 것과 인물이 변형된 것을 구분하지 못한다. 그래서 이 스킬은 시작 화면 일치만 숫자로 판정하고 그 뒤는 사람이 보게 한다. `gate clips`가 클립마다 키프레임과 0, 1.0, 1.5, 2.0, 3.0초 프레임을 한 줄로 늘어놓은 프레임 스트립을 만들고, 검수자가 이 이미지를 본 뒤 `qa/clips-review.md`에 판정을 남겨야 게이트를 통과한다.

검수 기록이 없으면 BLOCK, 기록을 남기면 PASS다. 사람의 판단을 생략할 수 없도록 절차 안에 박아 둔 셈이다. AI가 고도화될수록 사람의 역할이 줄어든다는 통념과 달리, 미묘한 판단이 필요한 자리에서는 사람의 눈이 오히려 더 중요해진다.

## 29가지 함정과 예방법

스킬에는 영상 제작에서 자주 생기는 함정 29가지가 증상, 원인, 예방법, 하네스 검사 ID와 함께 정리되어 있다(`references/gotchas.md`). README가 꼽은 것 몇 가지는 이렇다.

- G01: 클립은 시작 화면이 같아도 1~2초 뒤에 옷, 안경, 머리가 바뀐다
- G11·G12: 컷 길이는 초가 아니라 박의 배수로 정하고, 시작 프레임은 누적 시간에서 한 번만 반올림한다
- G13: 대사 길이를 먼저 재고 그다음 컷 길이를 정한다
- G21: `검사 | tail`처럼 파이프로 출력을 자르면 종료 코드가 사라진다
- G26: ffmpeg에서 `adelay` 뒤에 `apad`·`atrim`을 쓰면 지연이 사라지므로 `asetpts=N/SR/TB`가 필요하다
- G27: ICC 프로파일이 붙은 영상에서 `ffprobe -of csv=p=0`은 프레임 수를 `30,`처럼 출력하므로 `-of default=nw=1:nk=1`을 쓴다

README가 꼽은 항목만 봐도 생성 도구 특유의 문제(G01)와 함께 박자 계산, 종료 코드, ffmpeg 옵션처럼 영상 제작 자체의 함정이 섞여 있다. 사람이 편집해도 빠지는 구멍까지 AI에게 맡기기 전에 미리 막아 두는 장치다. AI로 영상을 만들어 보려는 교사에게도 그대로 확인 목록이 된다.

## 교육 현장에 적용할 때

이 스킬을 직접 설치해 써 보는 것도 좋은 경험이지만, 더 중요한 것은 단계별 품질 관리라는 발상을 우리 환경에 맞게 옮기는 일이다.

1. 자신만의 관문 만들기: 학습 목표와 영상 유형에 따라 제작 단계를 정하고 단계마다 확인 목록을 둔다. 예를 들어 개념 설명 영상이라면 정확성, 명확성, 몰입도를 확인 항목으로 삼는다.
2. 도구의 역할 나누기: README의 도구 목록은 이미지·영상 생성에 ChatGPT와 Grok Imagine, 음악에 Suno, 목소리에 ElevenLabs와 Fish Audio, 받아쓰기 검수에 whisper(검수 스크립트와의 연동은 아직 검증되지 않았다고 README가 밝힌다), 조립에 Remotion이다. Remotion 컴포지션 코드는 저장소에 들어 있지 않아 따로 설치해야 한다. 외부 도구의 무료 범위와 상업 이용 조건은 자주 바뀌니 작업 직전에 다시 확인하라고 README는 당부한다.
3. 사람의 검수 남기기: 교육 콘텐츠는 학습자의 이해, 흥미, 윤리적 적합성처럼 사람이 판단할 부분이 크다. 프레임 스트립 같은 보조 도구로 검수 효율을 높이되 판단 자체는 넘기지 않는다.
4. 실행 환경 확인하기: 하네스와 스크립트를 돌리려면 ffmpeg, ffprobe, Python 3, Bash가 필요하다. 윈도우에서는 `.sh` 스크립트를 WSL로 실행해야 한다. MIT 라이선스 오픈소스라 교과에 맞게 고쳐 쓸 수도 있다.

참고로 이 스킬은 브라우저 기반 영상 제작 서비스 SceneSteller를 만드는 팀이 영상 제작 과정에서 쌓은 점검 기준을 정리한 것이다.

AI 영상의 관문을 설계하는 일은 기술을 익히는 데서 끝나지 않는다. 교육적 의도와 품질 사이에서 어디에 선을 그을지 정하는 일이고, 그 선을 긋는 능력이 AI 시대 교사의 새로운 전문성이다.

## 복잡계의 피드백 루프로 보면

복잡계 이론에서 피드백 루프는 시스템이 원하는 상태에서 벗어날 때 그 차이를 되돌려 보내 바로잡는 장치다. `gate.py`가 하는 일이 이와 닮았다. 산출물이 기준에서 벗어나면 BLOCK이라는 신호를 돌려보내고, 고친 뒤에야 다음 단계로 넘긴다. 차이를 줄이는 쪽으로 작동하는 음의 피드백(negative feedback)이다. 여러 생성 도구가 얽혀 결과를 예측하기 어려운 제작 과정에 단계마다 이런 되먹임을 걸어 두면, 오류가 끝까지 번지기 전에 멈출 수 있다.
