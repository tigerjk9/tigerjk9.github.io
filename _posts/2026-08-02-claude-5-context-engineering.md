## 클로드 5, 더욱 영리해지다

최신 **클로드 5** 모델은 이전 세대 모델보다 훨씬 발전했다. 앤트로픽은 **클로드 오퍼스 5(Claude Opus 5)**와 **클로드 페이블 5(Claude Fable 5)** 같은 모델에서 **클로드 코드(Claude Code)**의 시스템 프롬프트 길이를 80% 이상 줄였으나, 코딩 평가에서 성능 손실이 없었다. 이는 모델이 스스로 판단하고 주변 콘텍스트를 활용하는 능력이 크게 향상되었음을 의미한다.

이러한 변화는 기존의 콘텍스트 엔지니어링 방식이 더는 최적이 아님을 보여준다. 앤트로픽은 **클로드 닥터(claude doctor)**라는 명령어를 도입해 스킬과 CLAUDE.md 파일의 크기를 자동으로 조정하는 방법을 제시한다.

## 과도한 제약 풀기

앤트로픽은 과거에 **클로드 코드**에 과도한 제약을 부여했다는 점을 발견한다. 시스템 프롬프트, CLAUDE.md 파일, 스킬 등이 서로 충돌하는 지시를 포함하는 경우가 많았다. 예를 들어 "필요시 문서 추가"와 "주석 절대 추가 금지" 같은 상반된 지시가 한 요청에 동시에 들어가는 식이다.

이러한 충돌은 **클로드**가 무엇을 할지 결정하기 전에 메시지를 더 신중하게 고려하게 만든다. 이전에는 파일 삭제 같은 최악의 시나리오를 방지하고자 제약이 필요했지만, 이제는 많은 제약을 제거하고 모델이 주변 콘텍스트와 판단력을 활용하게 할 수 있다.

또한 **클로드 코드**는 훨씬 많은 도구를 갖추게 되었다. 과거에는 CLAUDE.md가 메모리, 정보, 지침의 주요 출처였으나, 이제는 메모리, 아티팩트(artifacts), 스킬 등으로 세션 간에 콘텍스트를 로드하고 공유하는 새로운 방법을 제공한다.

## 달라진 콘텍스트 엔지니어링 전략

이전의 콘텍스트 엔지니어링 모범 사례 중 다수는 현재는 잘못된 통념이 되었다. 다음 표는 이전 관행과 새로운 접근 방식의 차이를 보여준다.

| 구분                  | 이전 관행 (Then)                     | 새로운 접근 (Now)                       |
|-----------------------|--------------------------------------|-----------------------------------------|
| **규칙 부여 방식**    | 명확한 규칙 제공 (예: 파일 삭제 방지)   | 모델의 판단력 활용 (예: 주석 밀도 조절)   |
| **도구 활용 지시**    | 사용 예시 제공                       | 도구 인터페이스 설계                    |
| **정보 제공 시점**    | 모든 정보 선제시                     | 점진적 공개 (필요할 때 제공)             |
| **지시 반복 여부**    | 지시 반복 (시스템 프롬프트, 도구 설명) | 간결한 도구 설명 (도구 설명에만 지시)     |
| **메모리 저장**       | CLAUDE.md에 수동 저장 (예: # 핫키)   | 자동 메모리 저장                        |
| **사양 참조 방식**    | 간단한 마크다운 사양 파일             | 풍부한 참조 (HTML 아티팩트, 테스트 스위트) |

각 변화에 대한 상세 내용은 다음과 같다.

*   **규칙 부여 방식:** 과거에는 **클로드 코드**가 파일을 삭제하는 등 최악의 시나리오를 피하도록 강한 지침을 주었다. 예를 들어, 시스템 프롬프트에 "코드에 주석을 작성하지 마라. 여러 단락의 독스트링이나 여러 줄 주석 블록을 만들지 마라"고 명시했다. 하지만 특정 프롬프트에서는 이러한 지침이 잘못될 수 있다. 새로운 시스템 프롬프트는 "주변 코드처럼 읽히는 코드를 작성하라: 주석 밀도, 이름 지정, 관용구를 맞춰라"로 바뀌었다. 모델이 스스로 판단하게 한다.

*   **도구 활용 지시:** 도구 사용법에 대한 가장 중요한 규칙은 예시를 주는 것이었다. 그러나 최신 모델에서는 예시가 오히려 탐색 공간을 특정하게 제한한다. 대신 도구, 스크립트, 파일의 인터페이스 디자인에 집중한다. 예를 들어, 할 일(Todo) 도구에서 `pending`, `in_progress`, `completed`와 같은 상태를 열거형으로 나열하면 **클로드**가 사용법을 유추한다.

*   **정보 제공 시점:** 과거에는 코드 검토 및 검증에 대한 자세한 정보를 시스템 프롬프트에 모두 포함했다. 하지만 **클로드 코드**는 이제 **점진적 공개(progressive disclosure)**에 매우 능숙하다. 검증 및 코드 검토를 별도의 스킬로 분리하여 필요할 때만 호출한다. 이 방식은 스킬뿐 아니라 도구에도 적용되어, 일부 도구는 '지연 로딩' 방식으로 필요할 때만 정의를 검색하여 콘텍스트 공간을 절약한다. CLAUDE.md 및 Skill.md 파일도 모든 가능한 관행을 중앙 저장소에 모으기보다, 필요할 때 로드할 수 있는 파일 트리를 구성한다.

*   **지시 반복 여부:** 이전 **클로드** 모델은 반복적인 지시가 필요하거나 콘텍스트 창의 시작보다 끝에 있는 지시를 더 잘 따르는 경향이 있었다. 이로 인해 시스템 프롬프트에 도구 참조가 포함되고 도구 설명에도 지시가 반복되었다. 이제는 이러한 반복 예시를 제거하고 도구 사용 지침을 시스템 프롬프트가 아닌 도구 설명에만 포함한다.

*   **메모리 저장:** 과거에는 사용자가 `CLAUDE.md` 파일에 ` #` 핫키를 사용해서 내용을 저장하도록 권장했다. 이제 **클로드**는 작업 및 사용자와 관련된 메모리를 자동으로 저장한다.

*   **사양 참조 방식:** 과거에는 계획 모드에서 마크다운 파일에 저장된 계획에 크게 의존했다. 사양을 코드베이스에 저장하여 장기 프로젝트에서 참조하도록 했다. 하지만 **클로드**는 이제 훨씬 더 복잡한 참조를 처리할 수 있다. 간단한 마크다운 파일 대신, 새로운 아티팩트 기능으로 생성된 HTML 아티팩트를 참조한다. 사양은 자세한 테스트 스위트나 다른 코드베이스의 함수 형태가 될 수도 있다. **루브릭(Rubrics)**도 참조의 한 형태이다. 루브릭은 동적 워크플로우를 사용하고 검증 에이전트를 가동하여 특정 분야(예: 좋은 API 디자인)에 대한 **클로드**의 판단을 검증하게 한다.

## 새로운 접근 방식 적용

새로운 콘텍스트 엔지니어링 원칙을 실제 프로젝트에 적용하는 방법은 다음과 같다.

*   **시스템 프롬프트:** 시스템 프롬프트는 제품 콘텍스트와 밀접하게 연관된다. **클로드**가 어떤 제품에서 어떤 작업을 수행하는지 알려준다. **클로드 코드**에서는 이 부분을 거의 수정하지 않지만, 자체 에이전트 하네스(agent harness)를 구축한다면 이 부분에 많은 시간을 투자해야 한다.

*   **CLAUDE.md:** CLAUDE.md는 가볍게 유지하고, 저장소의 목적을 간략히 설명한다. 대부분의 토큰은 코드베이스 내부의 문제점(gotchas)에 할애한다. 예를 들어, 모든 타입을 하나의 모놀리식 파일에만 두는 등 코드 조직에 대한 특별한 지침을 제공한다. 파일 시스템이나 저장소를 보면 **클로드**가 알 수 있는 '뻔한' 내용은 명시하지 않는다. 작업 검증 방법에 대한 여러 고유한 지침이 있다면, 검증 스킬을 만들고 CLAUDE.md에서 이를 참조하는 등 점진적 공개를 적극적으로 활용한다.

*   **스킬:** 스킬은 **클로드**가 필요할 때 정보를 찾도록 돕는 가벼운 가이드 역할을 한다. 매우 중요한 영역을 제외하고는 과도한 제약을 피한다. 긴 스킬의 경우, 가능한 한 점진적 공개를 활용하여 여러 파일로 나누어 분리한다. 스킬이 개인, 팀, 또는 제품에 특정한 의견, 지식, 또는 모범 사례를 담는 것이 가장 좋다.

*   **참조:** 파일을 @ 멘션하여 참조로 포함할 수 있다. 참조는 **클로드**가 현재 계획에 대한 심층 정보를 참고하게 한다. 이는 사양 파일, 목업(mockups) 또는 전체 코드베이스 형태를 띤다. 일반적으로 **클로드**가 잘 아는 언어로 명확하고 고충실도(high-fidelity) 지침을 제공하므로 코드 형태의 파일을 선호한다. 예를 들어, 디자인에 대한 HTML 목업은 디자인 설명이나 스크린샷보다 더 나은 결과를 만든다.

이러한 변화를 적용하고 **클로드 닥터** 명령어를 사용하여 콘텍스트를 간소화할 수 있다. 고급 모델 프롬프팅에 대한 더 자세한 내용은 **페이블 필드 가이드(Fable field guide)**에서 확인한다.

## 복잡계 이론의 시선으로 보면

시스템의 복잡성이 증가하면 통제 방식도 변한다. 이전에는 명시적 규칙과 직접적 통제가 안정성을 담보한다고 생각했지만, 이제는 시스템이 자체 판단력과 적응 능력을 발휘하도록 여백을 주는 것이 더 효과적이라는 사실을 보여준다. 이는 마치 복잡계 이론에서 미시적 규칙보다는 거시적 상호작용과 자율성에 기반한 **창발(emergence)** 현상이 더 강력한 결과를 낳는 것과 비슷하다. 시스템에 대한 과도한 제약은 오히려 유연성과 문제 해결 능력을 저해한다.
